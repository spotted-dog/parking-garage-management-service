## Architecture

This service follows the Swift server side framework Vapor architectural pattern and uses the modern Swift 6 concurrency async/await pattern. Vapor 4 documentation is located at https://docs.vapor.codes

The PostgreSQL data store for the development/test and production environments are managed separate from this service but this service needs the standard environment variable information to properly connect to the associated database. This includes:

- DATABASE_HOST
- DATABASE_PORT
- DATABASE_NAME
- DATABASE_SCHEMA
- DATABASE_USERNAME
- DATABASE_PASSWORD

NOTE: Local PostgreSQL will use .env.development and .env.testing files. For deployed to GCP, DATABASE_PASSWORD is fetched from the GCP Secret Manager where it is stored for development and production environments.

### Platform

This service is deployed and run on the Google Cloud Platform (GCP).

### Tech Stack

This is a Swift 6+ and Vapor 4+ based backend service. It follows modern Swift concurrency async/await patterns. Data storage is via a PostgreSQL database. Docker and Docker Compose are used for containerization so the service can be built, stored as an artifact and that artifact deployed into the desired environment.

Unit and Integration testing will use modern Swift 6 Swift Testing.

Leaf is used for the frontend which is already included with the Vapor framework. All UI work to the service should use Leaf.

Data passed from frontend to the backend and vis-versa is done via JSON.

### Current Implementation

The codebase is currently the stock Vapor scaffold: only a placeholder `Todo` resource exists (`Sources/ParkingGarageManagementService/Models/Todo.swift`, `DTOs/TodoDTO.swift`, `Migrations/CreateTodo.swift`, `Controllers/TodoController.swift`). None of the domain models in "Data Models" below (Garage, Floor, Space, Car, Reservation) are implemented yet — treat that section as the target design, not existing code.

The `Todo` resource shows the per-resource pattern to follow for new domain models:

- **Model** (`Models/`): a `final class` conforming to `Model, @unchecked Sendable`, using `@ID`/`@Field`/`@Parent`/`@Children` property wrappers, with a `toDTO()` conversion method.
- **DTO** (`DTOs/`): a `struct` conforming to `Content` with optional properties and `toModel()`/`toDTO()` conversions, used for request/response bodies instead of exposing the Fluent model directly.
- **Migration** (`Migrations/`): an `AsyncMigration` with `prepare`/`revert`, registered in `configure.swift` via `app.migrations.add(...)`.
- **Controller** (`Controllers/`): a `RouteCollection` grouping routes under a path and registering handlers marked `@Sendable`, registered in `routes.swift` via `app.register(collection:)`.

Tests (`Tests/ParkingGarageManagementServiceTests/`) use Swift Testing (`@Suite`/`@Test`) and `VaporTesting`, spinning up a real `Application` per test via a shared `withApp` helper that runs `autoMigrate()`/`autoRevert()` against the configured test database — there is no mocking of Fluent/the database.

`configure.swift` does not currently read `DATABASE_SCHEMA` or set a Postgres search_path — the `garage_manager` schema created by `sql/database_setup.sql` is not yet wired into the Fluent Postgres connection config in code.

### Data Models

Data models needed for this service include:

#### Garage

Represents the overall parking garage.

Includes properties:

- id (unique) generated by the service - not provided by the user
- name
- floors (one or more floors within a garage see model below)
- created_at the date/time this was first created in the service
- updated_at the latest date/time this was updated in the service

#### Floor

Represents a floor within a the garage.

Includes properties:

- id (unique) generated by the service - not provided by the user
- floor_number (unique ex. f1 for floor 1, f2 for floor 2 and such)
- parking_spaces (one or more parking spaces within a floor see model below)
- created_at the date/time this was first created in the service
- updated_at the latest date/time this was updated in the service

#### Space

Represents a parking space within a floor

Includes properties:

- id (unique) generated by the service - not provided by the user
- space_number (unique ex. 1001, 1002, 1003, etc.. for spaces on floor 1 and 2001, 2002, 2003, etc... for spaces on floor 2)
- available (defaults to true)
- parking_spaces (one or more parking spaces within a floor see model below)
- created_at the date/time this was first created in the service
- updated_at the latest date/time this was updated in the service

#### Car

Represents a car that is using the parking garage.

Includes properties:

- id (unique) generated by the service - not provided by the user
- license_plate
- reservations (one or more reservations - see model below)
- created_at the date/time this was first created in the service
- updated_at the latest date/time this was updated in the service

#### Reservation

Represents a car's reservation for a given space at at given time.

Includes properties:

- id (unique) generated by the service - not provided by the user
- reservation_date_time_in (date/timestamp for when the reservation started)
- reservation_date_time_out (date/timestamp for when the reservation started)
- floor_id (foreign key id of the floor for bidirectional lookup)
- space_id (foreign key id of the space for bidirectional lookup)
- car_id (foreign key id of the car for bidirectional lookup )
- created_at the date/time this was first created in the service
- updated_at the latest date/time this was updated in the service

## Deployment / Release

Deployments and releases for this service will be managed via GCP Cloud Run. Deployments should use the Docker artifact created with the GitHub CI/CD pipeline which is stored in the GCP Docker repository.

If the deployment is to the development/test environment, then the specified artifact in the GCP Docker repository should be used as is.

If the deployment is to the production environment, then the specified artifact in the GCP Docker repository should first be promoted to production and then deployed to the production environment.

Releases should be tagged using semantic versioning and a CHANGELOG.md file should be updated with the tag and it's associated changes.

CI/CD pipelines should be setup and managed using GitHub actions. The Docker artifact that is created should be stored in GCP Docker repository. The Docker artifact produced should be a development artifact that will be promoted to production when appropriate.

## Service API

Here are the requirements for the service.

### Garage Layout

- Manage floors within a garage
- Manage spaces (subsections within a floor)
- Define and manage parking spots with unique identifiers

### Parking Spot Management

- List all parking spots along with their availability status (available or occupied)
- Retrieve only available parking spots
- Update a spot's status (mark as occupied or available)

### Car Tracking

- Check a car in by making a reservation with an assigned available parking spot
- Check a car out by updating the reservation out timestamp and freeing up the assigned spot by marking it available
- Track check-in and check-out timestamps by starting and ending a reservation and keeping the reservation for historical data use
